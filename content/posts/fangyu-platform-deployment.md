这是我做的一个值班辅助平台，主要把登录、日常巡检、告警处理、办公网查询、设备操作和企业微信机器人放到一个入口里，尽量替值班人员省一些重复操作。各个业务服务和数据库仍然保持独立，方便维护和恢复。

## 整体架构

浏览器只访问 Nginx 暴露的正式入口。Nginx 再把请求转发给监听在本机回环地址上的平台主服务；平台统一处理登录、菜单、首页状态、业务 API 和审计日志。

巡检服务、机器人状态面板和机器人长连接保持独立。平台通过同源代理或只读聚合接入它们，而不是把所有业务代码和数据库硬合并在一起。Zabbix、DHCP、行为管理设备和防火墙也由后端适配器分别调用。

这种拆分有两个好处：一是统一入口和权限，二是某个外部系统不可用时，不会拖垮整个平台。例如文件共享服务不可达时，巡检报告仍然可以先保存到本地，页面明确提示共享状态即可。

## 服务边界和端口

正式入口只保留 Nginx 的 HTTP 端口。平台主服务、巡检服务和机器人面板都只监听本机地址，避免用户绕过统一登录直接访问业务端口。

典型组件包括：

- Nginx：负责正式入口和反向代理；
- 平台主服务：负责认证、用户、首页、审计和业务 API；
- 巡检服务：负责值班巡检、图片处理和 Word 报告；
- 机器人长连接：负责企业微信命令和告警确认；
- 机器人面板：提供只读运行状态；
- 自动确认任务：通过 systemd timer 在指定时间窗口处理测试告警。

旧的独立 Web 入口在迁移时不再继续保留。切换正式入口前，先确认新的内部健康接口正常，再让 Nginx 接管入口。

## 双网卡和路由

这类平台通常同时访问办公网、设备网和外部服务。双网卡配置的关键不是给两块网卡都设置默认网关，而是为特定目标增加精确路由：

- 主网卡承担用户入口和默认路由；
- 第二网卡访问设备网或数据库网段；
- 需要从主网卡访问的特殊目标，明确指定主网卡网关；
- 设备 API 的源地址固定为对应网卡地址。

迁移前应记录每个依赖的目标地址、端口、期望出口和源地址。修改远程主机的网络配置前，先备份配置，并确保拥有云控制台或本地控制台。使用 `netplan try` 比直接应用更安全，确认 SSH 没有断开后再正式应用。

验收时不要只测试端口能否连接，还要检查实际路由：

```bash
ip route get <目标地址>
timeout 3 bash -c '</dev/tcp/<目标地址>/<端口>'
```

## 外部系统适配

平台接入外部系统时，应该把登录、超时、重试、证书校验和返回值转换集中在适配器中，不要把设备 API 细节散落到前端。

### 告警数据库

如果平台直接查询告警数据库，建议建立专用的最小权限账号。只读页面只需要查询权限；真正的删除或确认操作才额外需要写权限。部署验收阶段只查询，不要为了证明删除功能而操作生产告警。

### DHCP 和主机名查询

办公网 IP 的主机名查询可以采用分层策略：

1. 先做 PTR 解析；
2. PTR 未命中时，再查询 DHCP 租约；
3. 对已经明确属于静态地址的网段，不再重复查询 DHCP。

这样可以减少 WinRM 请求，也能让“未发现”结果更容易解释。

### 行为管理和防火墙

设备 API 需要单独处理：

- Token 获取与刷新；
- TLS 证书指纹校验；
- 分页查询和去重；
- 批量大小限制；
- 写入后的回读验证；
- 超时后的查询确认，而不是盲目重复创建。

防火墙同步尤其要区分“平台标准地址库”和“设备当前镜像”。外部人员在设备上增加的地址，应在同步后进入镜像；只从一台设备删除时，平台不能擅自复制删除到另一台。只有两台设备都完成解封，平台标准库才删除该地址。

## 配置文件和敏感信息

环境文件只保存运行所需的凭据和外部系统参数，权限固定为 `0600`，所有者为 `root`。发布包、日志、截图和博客文档都不能包含：

- 密码；
- Token 和 Secret；
- Cookie；
- 私钥；
- 内部账号；
- 内部 IP、证书指纹和设备细节；
- 带有真实环境信息的配置文件。

示例配置只能保留变量名和占位符。首次创建超级管理员密码时使用环境变量，但恢复已有数据库后，账号密码以数据库为准，重新填写环境变量不会覆盖原密码。

## SQLite 备份

平台和巡检服务使用 SQLite 时，运行中的数据库不能简单地用 `cp` 复制。应使用 SQLite Backup API，或者先停止所有写入服务，再进行一致性备份。

备份至少要覆盖：

- 平台数据库；
- 巡检数据库；
- 机器人审计数据库；
- 报告目录；
- 临时草稿目录；
- 环境文件；
- systemd 单元；
- Nginx 配置；
- 网络配置；
- 当前发布包。

备份完成后生成校验清单，并把包含明文环境文件的目录限制在受控的 root 备份位置。不要只备份代码：用户、会话、审计记录、报告索引和设备镜像都在运行数据里。

## 迁移顺序

一个相对稳妥的恢复顺序是：

1. 安装系统软件和 Python 运行环境；
2. 配置网卡、DNS 和精确路由；
3. 上传发布包和备份；
4. 安装程序，但暂不开放正式入口；
5. 停止平台、巡检和机器人服务；
6. 恢复环境文件、数据库和报告目录；
7. 恢复机器人程序及 systemd 单元；
8. 修正目录所有权和文件权限；
9. 启动后端服务和机器人；
10. 逐项检查外部依赖；
11. 最后切换 Nginx 正式入口。

恢复数据库前必须先停止写入服务。恢复后不能只看 systemd 的 `active`，还要逐个调用内部健康接口，并检查日志中是否存在连接失败、认证失败或后台任务异常。

## 验收清单

基础验收至少包括：

- Nginx、平台、巡检和机器人服务处于运行状态；
- 内部健康接口返回成功；
- 超级管理员和普通用户登录正常；
- 用户管理和审计权限边界正确；
- 手机端巡检没有横向溢出；
- 图片上传、草稿保存和 Word 报告生成正常；
- 文件共享不可用时不会虚报上传成功；
- 告警查询正常，写操作只使用批准的测试对象；
- DHCP、行为管理和两台防火墙的状态显示准确；
- 企业微信机器人命令、只读面板和定时任务正常；
- 审计记录包含用户、时间、来源和结果。

写操作验收必须单独安排。删除告警、封禁地址、解封地址和确认告警都会改变外部系统，不能用生产对象随意测试。

## 常见故障思路

遇到 Nginx `502` 时，先看后端服务状态和本机健康接口，再看 Nginx 配置。巡检报告失败时，区分是本地目录权限、数据库、图片处理还是共享服务不可达。DHCP 离线时，先检查 WinRM 端口和账号权限，不要先改默认路由。设备证书校验失败时，人工确认新指纹后再修改配置，不要直接关闭证书校验。

如果只有一台防火墙离线，先检查目标路由、源地址、端口和 TLS 能力，再决定是否重试。机器人定时任务则要同时检查 systemd timer 的时区、任务窗口和实际日志，不能只比较服务器的 UTC 时间。

## 回滚原则

代码问题优先只回滚 `/opt` 下的发布代码，保留 `/var/lib` 中的运行数据。只有确认数据库损坏或迁移失败时才回滚数据库；数据库回滚会丢失备份时间之后的用户、审计、巡检、报告索引和设备镜像变化，因此回滚前要再次备份当前数据库。

Nginx 切换脚本必须保留旧配置备份，回滚时先恢复配置、执行 `nginx -t`，再 reload。任何回滚都应以健康接口和页面验收为结束条件，而不是只看命令是否返回成功。
